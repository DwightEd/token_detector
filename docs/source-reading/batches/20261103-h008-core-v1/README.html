因果轴：为什么是 P+K 输入、K+EOS 目标

令 prefix_ids 长 P，字面候选在完整聊天条件后的 token 为 c[0:K]，EOS 为 e。不能用独立 encode(candidate)替代上下文 suffix。completion_metadata先检查模板字符串编码=模板ID，再检查 encode(prefix+candidate) 的前P项仍为同一prefix；最后要求suffix原样decode回完整姓名。聊天前缀已有轮次结束 EOS 可以保留，禁令只针对姓名 suffix 内含 EOS。聊天模板控制token和 assistant提示的含义按固定版本核对，见 Transformers4.57.1 chat templates。

\[ x=(p_0,\ldots,p_{P-1},c_0,\ldots,c_{K-1}),\qquad |x|=P+K, \]
\[ t=(c_0,\ldots,c_{K-1},e),\qquad |t|=K+1. \]

零基位置 P−1+j 的 causal输出预测 t[j]，j=0,...,K。第一姓名token由 prefix末位置预测；最后一个姓名token的输出预测 EOS。终止EOS是 target，不是本次输入末尾附加token，避免把“终止之后预测什么”误当“终止本身概率”。

对象 轴/长度 dtype及所有权
prefix_ids / candidate_token_ids Python列表 [P] / [K] 非负内置int；新列表，非batch张量
input_ids / target_token_ids [P+K] / [K+1] 姓名全长，targets额外含一次EOS
target_prediction_positions [K+1]，值为 P−1,...,P+K−1 元数据，不是显式传给模型的cache_position
encoded / attention_mask [1,P+K] torch.long/int64，CUDA:0；mask全1只表示无padding，模型内部另建causal mask
output.logits [1,K+1,V] 本函数要求浮点且全有限；父模型按FP16/NF4配置加载，但此检查不强制logits必须FP16
rows=logits[0].double() [K+1,V] 明确float64，用于完整词表归一化；不能恢复原低精度forward信息
normalizers / selected / logp 各 [K+1] 取回Python浮点；joint用fsum，不作长度平均

为什么 logits_to_keep=K+1 正好取到这些位置？固定 Transformers4.57.1 的 Qwen2 causal LM 对最后 N 个 hidden-state位置应用词表head；N=K+1时，长度P+K的起点就是P−1。它只减少需要输出的词表行，不会省去整个prefix的因果计算。调用没有传 labels，也没有 loss/backward。固定版API与同tag官方实现相符；没有借新版文档替换旧版行为。

每个目标位置都先对 V个词表项 计算 normalizer，再取被观测姓名或EOS的目标logit：

\[ z_j=\log\sum_{v=0}^{V-1}\exp(\mathrm{rows}_{jv}),\qquad \ell_j=\mathrm{rows}_{j,t_j}-z_j,\qquad \ell(c+\mathrm{EOS}\mid S,Q)=\sum_{j=0}^{K}\ell_j. \]

dim=-1 消去词表轴，留下K+1行，使用数值稳定的 logsumexp；不是只在“两个人名目标token”里归一化。PyTorch2.8官方LSE。之后另一个文件的 candidate_distribution 才将两条完整序列的 logP归一化为 q。q条件于有限候选池；它不自动成为校准事实概率，也没有消除姓名长短/频率先验。
