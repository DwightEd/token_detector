首轮拒绝时可用主存为 **2,525,605,888 B**，小于预冻结的 **2,684,354,560 B（2.5 GiB）**。一次零模型导入诊断观察到 CLI 比直接调用同一 canonical `.run` 多用约 48.086 MiB 私有内存，小于原约 151 MiB 缺口；系统空闲内存也随时间变化，不能将首轮失败唯一归因于 CLI。随后独立登记的轻量调用复用原 M0，原方法和资源门不变。其导入并完成六项 token 计数后，主存可用 **2,751,553,536 B**，GPU 可用 **7,283,408,896 B**；这只是 preflight 通过，不能保证生成峰值。

实际生成第三项输入 2924 tokens，在 SDPA 请求额外 522 MiB 时 OOM。报错时 PyTorch 已分配约 2.60 GiB，冻结 allocator 上限为 3 GiB，而物理 GPU 尚余约 3.90 GiB。故不能称整块 GPU 已耗尽；也不能凭物理空闲量宣称该固定配置可运行。第三项只有 prefill 入口、无成功返回，部分生成 token 数维持 unknown；其余三项未启动。错误、部分 forward 与前两份完整原始输出均保留，无自动重试。

原预算上限为六个生成请求，每请求输入不超过 4096 tokens、输出不超过 1536 tokens；六个请求不等于六次模型 forward。本轮复用本地 Qwen2.5-3B-Instruct NF4 仪器，其确定性解码包含既有 repetition penalty 1.05，不能描述为裸 logits 的直接 argmax。全部六项实际输入在加载前计数。前两份输出并非因长度截断或模型主动弃答而 unknown，而是未满足预冻结的 coverage 结构；原始输出不改写、不手工补救。

固定必要门要求四个原始来源各至少一个获许可的 complete 关系；前两项完整输出均无可用 complete，因此本轮已不可能通过该门。独立语义汇总覆盖 16 项义务、31 个被 validator 记为 unknown 的 anchors；另外 45 项义务、213 个预定 anchors 与两项对照未评价，未将第三项失败的 partial payload 作语义判断。错误 complete 的语义数量不可评，不能把零获许可记录说成零错误或可靠弃答。
